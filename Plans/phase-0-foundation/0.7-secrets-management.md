# Step 0.7 — Secrets Management (AWS SSM Parameter Store)

## Status
SCAFFOLD — code + script + docs written, user-blocked on AWS BAA + KMS key
+ SSM hierarchy provisioning (Phase B terraform).

## Supersedes
Doppler-based approach (see `AWS-ONLY-MIGRATION.md`). Doppler was dropped
to consolidate under the AWS BAA and eliminate a second vendor.

## Objective
Production secrets live in AWS SSM Parameter Store as SecureStrings, KMS-
encrypted. The ECS task IAM role fetches its env's parameters at container
boot. Local dev continues to use `.env` files.

## Pieces (DONE in Phase A)

### Loader — `packages/config/src/secrets.ts`
- `loadSecrets(env: 'dev'|'stg'|'prd'): Promise<Record<string,string>>`.
- If `NODE_ENV !== 'production'` → returns `{}`. Local `.env` wins.
- Else: `@aws-sdk/client-ssm` `GetParametersByPathCommand`, path
  `/medical-crm/${env}/`, `Recursive: true`, `WithDecryption: true`.
- Paginates via `NextToken`. Caches result for process lifetime.
- Strips the path prefix so callers see bare variable names.

### Bootstrap — `apps/api/src/bootstrap.ts`
- Pulls env from `APP_ENV` (`dev`|`stg`|`prd`). Defaults to `dev`.
- Merges SSM values into `process.env` without overwriting anything the
  container already has set — enables emergency operator overrides via
  ECS task env without rotating SSM.
- Called from `apps/api/src/index.ts` inside the `serve()` boot chain,
  after the first-line `./tracer` import (X-Ray init is env-independent
  and safe to run before SSM fetch).

### Next.js web
Next reads env at runtime from the ECS task env block. The web container's
entrypoint can optionally export SSM params as env before `node server.js`,
but for Phase A we rely on the single source of `NEXT_PUBLIC_*` coming
from SSM via an entrypoint shim (Phase B detail — parked).

### Bootstrap script — `scripts/ssm-setup.sh`
- Args: `<env>` where env ∈ dev|stg|prd.
- Reads keys from `.env.example`, skips local-only keys
  (`AI_CHANNEL_IDENTITY`, `DEV_AUTH_*`, `NODE_ENV`, `PORT`, `LOG_LEVEL`).
- For each key: checks `aws ssm get-parameter --with-decryption`; if
  missing, prompts and writes a SecureString with `alias/medical-crm`.
- Never overwrites — rotate explicitly via `--overwrite`.

### IAM policy snippet (Phase B terraform)
```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["ssm:GetParametersByPath"],
      "Resource": "arn:aws:ssm:us-west-1:${account}:parameter/medical-crm/${env}/*"
    },
    {
      "Effect": "Allow",
      "Action": ["kms:Decrypt"],
      "Resource": "arn:aws:kms:us-west-1:${account}:alias/medical-crm"
    }
  ]
}
```

## Workflow changes (DONE in Phase A)
`.github/workflows/ci.yml` — Doppler CLI install + `doppler run --` wrappers
removed. CI runs creds-free (lint/typecheck/build only).

`.github/workflows/deploy.yml` — OIDC auth, ECR push, ECS deploy. Does NOT
grant itself SSM read — the deployed container fetches at boot.

## Open question (Phase B)
Next.js `next.config.ts` is out-of-process (build-time) and doesn't go
through `loadSecrets`. The web container entrypoint script should export
SSM params to env before `node server.js` to cover any `NEXT_PUBLIC_*` that
isn't baked at build time. Decision deferred until Phase B terraform drafts
the task def — at which point we either wire an entrypoint shim or move
`NEXT_PUBLIC_*` wholly to build-time injection via GH Actions.

## Rotation runbook (from `docs/SECRETS.md`)
1. `aws ssm put-parameter --overwrite` in the target env.
2. `aws ecs update-service --force-new-deployment`.
3. Verify.
4. Revoke the old credential at the source system.
5. Log in the audit calendar.

## Hard rules
See `docs/SECRETS.md` § Hard rules. Highlight: never put `DEV_AUTH_*` in
stg/prd SSM — the `assertDevAuthNotInProd` guard will crash-loop the
container. That is the intended fail-closed behavior.
